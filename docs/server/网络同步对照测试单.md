### 0.3 记住三个数字

后面每一条都会用到，先记下来免得来回翻文档：

| 名称 | 值 | 从哪来 |
| --- | --- | --- |
| 静止高度 | **y ≈ 0.55** | 地面顶面 y=0.05 + 方块半高 0.5 |
| 起点高度 | **y = 1.5** | `network-demo.scene` 里 Player1/Player2 的初始 Translation |
| 场景尺寸 | **3487 字节** | 握手时下发的场景 YAML 长度，用来核对握手是否正常 |

场景里一共 4 个实体，测试时用来辨认：

| 实体 | 颜色 | 初始位置 | 刚体类型 |
| --- | --- | --- | --- |
| 地面 | 灰 (0.8, 0.8, 0.8) | 原点 | Static（不同步） |
| **Player1** | **蓝** (0.2, 0.6, 1) | (-2, 1.5, 0) | Dynamic（同步） |
| **Player2** | **橙** (1, 0.6, 0.2) | (2, 1.5, 0) | Dynamic（同步） |
| 障碍物 | 黄 (0.9, 0.9, 0.3) | (0, 0.6, -3) | Static（不同步） |

> 服务器**只同步 Dynamic 刚体**。所以灰色地面和黄色障碍物在快照里根本不出现 ——
> 这是设计如此，不是 bug。如果看到只有 2 个同步实体（蓝 + 橙），就是对的。

## A 部分：协议冒烟测试（自动化，1 分钟）

这一部分**不需要开图形界面**，全程命令行。它覆盖 5 条链路，是后面所有结论的地基。
**请先跑完 A 再进 B** —— 如果 A 挂了，B 的现象无法解读。

### A.1 启动服务器

**开终端 A**，在仓库根目录执行：

```bash
./build/Server/RelWithDebInfo/Server.exe --scene assets/scenes/network-demo.scene
```

- ✅ **应该看到**（这是 2026-10-01 实测的完整序列，行号对应实际日志位置）：

  ```text
  [Server] Project root: C:/.../feature-network-server-4cd1af4f
  [Server] scene='assets/scenes/network-demo.scene' duration=0s tickRate=60Hz port=30000
  [SceneLifecycle] RuntimeStart backend=Bullet, entities=4
  [Server] Runtime started, stepping physics at 60Hz
  [NetServer] Listening on port 30000
  [Server] Scene payload prepared: 3487 bytes
  [SessionMgr] Slot 1 bound to entity 'Player2'
  [SessionMgr] Slot 0 bound to entity 'Player1'
  ```

- ⚠️ **关键核对点**：

  | 行 | 核对什么 |
  | --- | --- |
  | `Project root: ...` | 路径必须**指向本仓库**。指到别处 = 场景和资源都加载不对 |
  | `tickRate=60Hz port=30000` | 参数解析正确 |
  | `entities=4` | 场景确实加载了 4 个实体 |
  | **`Scene payload prepared: 3487 bytes`** | **这个数字必须记下**，A.2 的 `[1/5]` 会核对 |
  | `Slot 0 bound to entity 'Player1'` | 0 号槽 = Player1 = 蓝色的那个 |
  | `Slot 1 bound to entity 'Player2'` | 1 号槽 = Player2 = 橙色的那个 |

- ⚠️ 启动过程中会刷一大片 `[ComponentLifecycle] Add ... -> entity N` 的日志，
  4 个实体 × 5 个组件 = 20 行左右。**这是正常的**，不需要关注。

- ⚠️ **`Slot` 两行出现在最后**（`SessionManager` 初始化时机在监听之后），
  所以判断启动成功要看 **`Scene payload prepared`** 那行，它在 `Slot` 之前。
  整段日志在**同一秒内**打完，如果只看到一半，稍等片刻。

- ❌ **如果报 `[Server] Failed to start network on port 30000`**：端口被占用，
  先跑 0.2 的清理命令。或者换个端口：加 `--port 30001`（B 部分连接时也要改成 30001）。

- ❌ **如果报 `[Server] Failed to load scene 'assets/scenes/network-demo.scene'`**：
  检查是不是**不在仓库根目录**执行的。程序会自动探测项目根目录，
  但从根目录启动最稳。也可以改用绝对路径传给 `--scene`。

**这个终端不要关**，A.2 和 B 部分都要用它。

### A.2 跑冒烟脚本

**开另一个终端 B**，同样在仓库根目录执行：

```bash
python tests/manual/net_smoke.py
```

> 如果系统 `python` 不在 PATH，用完整路径：
> `"C:/Users/liu69/.workbuddy/binaries/python/versions/3.13.12/python.exe" tests/manual/net_smoke.py`

- ✅ **应该看到**（这是本机 2026-10-01 两次实测的输出，你的数字会有小幅波动）：

  ```text
  [1/5] Welcome: player=P1, scene=3487B
  [2/5] Pong: RTT 27.7ms, 时间戳回显一致
  [3/5] Snapshot: 收到 16 帧（tick 86 → 131），2 个 Dynamic 实体
  [4/5] 水平输入生效：Player1 z 0.09 → 3.80 (Δz=+3.72)
  [5/5] 重力正常：抬升至 y=2.32，松手后回落 1.78m 到 y=0.55（静止高度约 0.55）
  PASS
  ```

- ⚠️ **逐项对照（不要只看最后的 PASS）**：

  | 行 | 核对什么 | 可接受的波动 |
  | --- | --- | --- |
  | `[1/5]` | **`scene=3487B` 必须正好等于** A.1 日志里的数字 | 无波动，必须一致 |
  | `[1/5]` | `player=P1` 必须是 P1（脚本占 0 号槽） | 无波动 |
  | `[2/5]` | RTT 在 0.1 ~ 50ms 之间 | 实测 27-33ms，波动正常 |
  | `[3/5]` | **`2 个 Dynamic 实体`** 必须是 2 | 无波动 |
  | `[3/5]` | 帧数 ≥ 3（20Hz × 1.5s 理论约 30 帧，实测 10-16 帧） | **10-30 都算过**，见下注 |
  | `[4/5]` | **Δz 必须 > 0.5**（实测稳定在 +3.72） | 只要 > 0.5 就算过 |
  | `[5/5]` | **回落幅度必须 > 1.0**（实测 1.78-2.02） | **1.5-3.0 都正常** |
  | `[5/5]` | 最终落点 **y ≈ 0.55**（0.50-0.60） | 对应前面记的「静止高度」 |
  | 退出码 | **必须是 0** | `echo $?` 可查 |

  > **为什么帧数只有十几帧？** 脚本按 20Hz 发输入、服务器也按 20Hz 广播快照，
  > 理论 1.5 秒应有 30 帧。但脚本是**非阻塞收包**，连上时可能已经错过了几帧，
  > 而且收包循环有 `sleep(0.005)` 的调度抖动。实测稳定在 10-16 帧，
  > 断言阈值设在 ≥3 是留了充足余量的。**帧数少不代表有问题。**

- ✅ **退出码检查**（顺手做一下）：

  ```bash
  python tests/manual/net_smoke.py; echo "退出码=$?"
  ```

  应该打印 `退出码=0`。

### A.3 对照服务器日志（强烈建议做 —— 这里能看到重力修复的直接证据）

回到**终端 A**，看服务器那边同时打印了什么。这是 2026-10-01 实测的一段：

```text
[Server] Hello from 'Editor' (protocol v1)
[Server] Welcome sent to session 1: player=0 scene=3487 bytes
[Server] tick=120 entity=17100000000000000003 pos=(2.00, 0.55, 0.00)
[Server] tick=120 entity=17100000000000000002 pos=(-2.00, 0.55, 2.81)
[Server] tick=180 entity=17100000000000000003 pos=(2.00, 0.55, 0.00)
[Server] tick=180 entity=17100000000000000002 pos=(-2.00, 3.69, 3.97)
[Server] tick=240 entity=17100000000000000003 pos=(2.00, 0.55, 0.00)
[Server] tick=240 entity=17100000000000000002 pos=(-2.00, 0.58, 3.97)
```

- ⚠️ **怎么读这段**：盯住 `entity=...0002` 那一列，它就是脚本控制的 Player1。

  | tick | pos | 脚本当时在做什么 | 说明 |
  | --- | --- | --- | --- |
  | 120 | `(-2.00, **0.55**, 2.81)` | 按住 W 前进中 | z 从 0 涨到 2.81；y=0.55 已落地 |
  | 180 | `(-2.00, **3.69**, 3.97)` | 按住 Q 抬升中 | **y 升到 3.69**；z 停在 3.97（松了 W） |
  | 240 | `(-2.00, **0.58**, 3.97)` | 松开 Q，自由落体后 | **y 掉回 0.58**，落回地面 |

- ⚠️ **这就是重力修复的直接证据**：
  - tick 180 → 240 之间（1 秒），y 从 **3.69 掉到 0.58**，掉了 **3.1 米**
  - 如果是修复前的 bug，这 1 秒只会掉约 **0.16 米**（3.69 → 3.53）
  - **肉眼判据：1 秒内 y 从 3.69 变到 0.58 = 正常；只变到 3.5x = bug 复现**

- ⚠️ `entity=...0003`（Player2）全程死钉在 `(2.00, 0.55, 0.00)` —— 正确，
  脚本没控制它，它就一直静止在地上。

- ⚠️ 服务器每 **60 tick（=1 秒）** 打印一次，所以只有 3-4 行，正常。
  `tick=` 后面的数字是 60 的整数倍就是这个原因。

### B.4 检查点 1 — 场景自动加载并进入播放态

- ✅ **应该看到**（两个窗口应该长得一样）：

  - **橙**色方块，位置偏右（世界坐标 x=+2）

### B.5 检查点 2 — 玩家槽位分配正确

**在两个窗口分别操作**：

1. 点菜单栏 **「网络」**
2. **不要点任何东西**，直接看菜单最下面那行灰字（`ImGui::TextDisabled`，不可点击）

- ✅ **应该看到**：
  - 一个窗口显示 **`已连接 (P1, RTT XXms)`**
  - 另一个窗口显示 **`已连接 (P2, RTT XXms)`**

- ⚠️ **核对点**：
  - **两个窗口的 P 编号必须不同**（一个 P1 一个 P2）。都是 P1 或都是 P2 = bug
  - 谁是 P1 不确定也没关系，**先开的窗口通常是 P1**（对应 B.3 的连接顺序）
  - `RTT` 应该是几十毫秒的量级（本机 20-35ms）。显示 `RTT 0ms` 或 `RTT 几万 ms` 都不对

- ❌ **如果显示「未连接」**：连接掉了。回 B.3 重连。
- ❌ **如果两个都是同一个 P 编号**：槽位分配有问题，记录现象。

### B.6 检查点 3 — 输入驱动 + 双端同步（核心项）

这是 B 部分最重要的一条，**请慢一点做**。

**准备工作**：**先点击窗口 1 的视口区域**（就是显示 3D 场景的那块），
确保它拿到键盘焦点。不点的话按键会被 ImGui 面板吃掉。

**然后按住 W 键约 1.5 秒**，松开。

- ✅ **应该看到**：
  - **窗口 1 里**：蓝色方块（P1）沿着 **+Z 方向**（朝屏幕里 / 远离相机）移动
  - **窗口 2 里**：同一个蓝色方块，**同样移动了大致相同的距离**

- ⚠️ **核对点**：
  - 两个窗口里蓝方块的**移动方向必须一致**（不能一个往前一个往后）
  - 移动距离**大致相同**（窗口 2 可能略有延迟，见下）
  - 窗口 1 的**橙色方块不能动**（W 只控制自己的方块）

- ⚠️ **关于延迟**：窗口 2 里看到的位置比窗口 1 晚约 **100ms**，
  这是**插值延迟**（`kInterpDelaySec = 0.1`），设计如此，**不是 bug**。
  松手后两个窗口最终停下位置应该一致（视觉上无差别）。

**接着测其余按键**，每次按完松开，两边都看一眼：

| 按键 | 自己的方块应该 | 方向 |
| --- | --- | --- |
| **W** | 远离相机 | +Z |
| **S** | 靠近相机 | -Z |
| **A** | 向左 | -X |
| **D** | 向右 | +X |
| **Q** | **向上升起** | +Y |
| **E** | **向下压** | -Y |

- ⚠️ **重点测 Q 和 E**：这两个是 2026-10-01 这次修复直接改动的路径。
  - 按 **Q**：方块应该**明显升到空中**（按住 1 秒约升 5 米）
  - 松开 Q：方块应该**明显自由落体掉回地面**，落在地上（y≈0.55）后**停住不动**
  - 按 **E**：方块应该被压向地面，但因为地面挡着，实际上不太看得出来

- ⚠️ **再测组合键**：同时按 **W + Q**，方块应该**斜着往斜上方飞**
  （前进 + 上升同时生效），说明按键位是独立的、可以叠加。

- ❌ **如果按键完全没反应**：
  - 确认**点过视口**了（焦点问题，这是最常见原因）
  - 确认按键时**没有在 ImGui 输入框里打字**（比如连接对话框还开着）
  - 看 Editor 日志有没有 `[NetSession]` 相关警告

- ❌ **如果窗口 1 动了但窗口 2 不动**：
  说明上行通了、下行没通。记录窗口 2 的网络菜单状态和它的日志。

### B.7 检查点 4 — 重力行为正常（本次修复的验收点）

**在任意一个窗口**（比如窗口 1）：

1. 按住 **Q** 约 1 秒，让方块升到空中（升到 y≈3~5）
2. **松开 Q，什么都不按**
3. **盯着方块看 3 秒**

- ✅ **应该看到**：方块**明显下坠**，感觉是「掉下来」的，
  大约 **0.9 秒**就砸到地面，然后**停在地面上不动**。

- ❌ **如果看到「缓慢飘落」**：方块像羽毛一样慢慢往下沉，
  要 **5 秒以上**才落到地面，而且落得很均匀 —— **这就是 bug 复现了**。
  这个现象说明重力又被清零了，服务端退回成了「匀速下沉」。

- ⚠️ **量化对照**（如果想更严格）：修复前后就差这一点：

  | 版本 | 松手后 3 秒内回落 |
  | --- | --- |
  | ✅ 修复后 | 约 **2.0 米**（一秒内就落地了） |
  | ❌ 修复前（bug） | 约 **0.1 米**（3 秒才挪一点点） |

  肉眼判据：**松手后 1 秒内应该已经落地**。如果 1 秒了还悬在半空慢慢降，就是 bug。

- ⚠️ **同时看窗口 2**：另一个窗口的方块也应该同步下坠。
  如果窗口 1 掉下来了但窗口 2 悬着，那是同步问题不是重力问题。

- ❌ **如果确认是缓慢飘落**：跑一次 A 部分的冒烟脚本，
  它会给出精确数字并直接报错定位（这是它的设计用途）。

### B.8 检查点 5 — 断开连接的行为

**在窗口 1（刚才当 P1 的那个）操作**：

1. 点菜单栏 **「网络」**
2. 点 **「断开连接」**

- ✅ **应该看到**：
  - 窗口 1 的网络菜单状态变回 **`未连接`**
  - **窗口 2 的方块继续正常显示**，不受影响
  - 窗口 1 里方块**停在原地**（不再被服务器驱动），但场景还在、还能继续看
  - 窗口 2 的网络菜单**仍然显示 `已连接 (P2, ...)`**

- ⚠️ **核对点**：断开的一方**不能影响**没断开的一方。这是基本的隔离性。
- ⚠️ 断开后窗口 1 应该能**重新连接**（回 B.3 再连一次），槽位可能变。
- ❌ **如果窗口 2 也跟着断了**：记录现象，这是服务端会话管理的问题。

## D 出问题时的自助排查

### 最常见的 3 个坑

1. **按键没反应** → 没点视口，焦点还在 ImGui 面板上。点一下 3D 视口再按。
2. **连不上服务器** → 残留的旧 `Server.exe` 占着端口，或防火墙拦了。
   跑 0.2 的清理命令；防火墙弹窗要「允许」。
3. **不在仓库根目录执行** → 程序虽然会自动探测项目根目录，
   但从根目录启动最可靠。报 `Failed to load scene` 基本都是这个。

### 已修复的两个 bug（若你用的是旧构建会复现）

这两个都是本次会话定位并修掉的，症状很容易被误判成「测试脚本坏了」：

| 症状 | 真实原因 | 修复位置 |
| --- | --- | --- |
| 冒烟脚本 `FAIL: 按住 W 后未前进：Δz=0.000`，但服务器日志显示 `inject ... vel=(0.00,0.00,5.00)` 注入成功 | 方块落地静止约 1s 后 Bullet 把它**休眠**了（`active=0`）。`setLinearVelocity()` 不会唤醒已休眠的刚体，`stepSimulation` 跳过 inactive island，速度同一 tick 就被丢弃 | `BulletPhysicsWorld::SetEntityLinearVelocity` 注入后补 `body->activate(true)` 并 `setActivationState(DISABLE_DEACTIVATION)` |
| 点菜单「连接服务器...」**什么都不弹** | `BeginPopupModal` 只是"画"，让弹窗出现的是同一帧的 `ImGui::OpenPopup()`。旧代码只置了一个 bool，且菜单动作与弹窗绘制不在同一 ImGui 上下文，弹窗 ID 对不上 | `NetworkSessionController::OpenConnectionDialog` 改为置请求位，`DrawDialog()` 里在正确上下文调 `ImGui::OpenPopup("连接服务器")` |

> **为什么第一个 bug 特别像脚本问题**：服务器上若已跑了很久（tick 上千），方块
> 早就休眠，无论脚本怎么写都测不出位移；而重启服务器后的第一次测试，
> 方块还在下落/刚落地，反而能过 —— 于是表现为「时好时坏」。
> 另外它和「0 号槽被编辑器占着」无关，占不占槽都会复现。

## 附：如果没有 build 目录

先做一次性构建（约 15-40 分钟，主要耗时在 vcpkg 装 asio 和 ffmpeg）。

```bash
# 0) 清掉可能导致 MSBuild 报错的代理变量大小写冲突
unset HTTP_PROXY HTTPS_PROXY

# 1) 配置（首次会拉 vcpkg 依赖）
"C:/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --preset default

# 2) 先构建 Server（测试用不到 Editor 也能跑 A 部分）
"C:/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --build build --config RelWithDebInfo --target Server

# 3) 再构建 Editor（B 部分需要）
"C:/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/Common7/IDE/CommonExtensions/Microsoft/CMake/CMake/bin/cmake.exe" --build build --config RelWithDebInfo --target Editor
```

> **为什么要 `unset HTTP_PROXY HTTPS_PROXY`**：本机环境同时存在大写和小写的代理变量，
> MSBuild 处理环境变量时不区分大小写，会报 `System.ArgumentException: 已添加项。
> 字典中的关键字:"HTTPS_PROXY" 所添加的关键字:"https_proxy"`，
> cmake 则表现为 `No CMAKE_C_COMPILER could be found`。清掉大写的那份即可。
> （小写的留给 curl/git 用，不影响。）

如果卡在 vendor 子模块为空（报找不到 glfw/spdlog 等的 CMakeLists.txt），
需要先补齐子模块：

```bash
git submodule update --init --recursive
```

> 如果这步因为网络（代理 502）失败，见下面「vendor 子模块离线补齐」。

构建报 `error C1083: 无法打开包括文件: "vulkan/vulkan.h"` 的话，
说明代码里又出现了漏加宏保护的地方 —— 这是**代码问题不是环境问题**，
默认 preset 下不应该报这个错。见 `docs/server/testing.md` §6。

## 附：vendor 子模块离线补齐

如果 `git submodule update --init --recursive` 因网络失败（代理 502 或 github 不通），
可以让子模块直接从主仓库自己的 `.git/modules` 拉取，完全绕开网络。
**下面这段可以直接整段复制执行**：

```bash
ROOT="$(git rev-parse --show-toplevel)"

for s in $(git config -f .gitmodules --get-regexp '^submodule\..*\.path$' | awk '{print $2}' | sed 's|^vendor/||'); do
    echo "== 补齐 vendor/$s"
    git config "url.$ROOT/.git/modules/vendor/$s.insteadOf" "$(git config "submodule.vendor/$s.url")"
    git -c protocol.file.allow=always submodule update --init "vendor/$s" || echo "  !! $s 失败"
done

echo "== 核对（每行开头是空格 = 已就位，是 - = 还没补）"
git submodule status
```

补齐后应能看到 **10 个子模块全部以空格开头**：

```text
 c35200e3... vendor/assimp (Release3.1_RC1-...)
 63c4d67e... vendor/bullet3 (3.25-27-g63c4d67e3)
 e08302e1... vendor/entt (v3.16.0-296-...)
 cc61c688... vendor/glfw (3.4-82-gcc61c688)
 e7970a8b... vendor/glm (0.9.5.3-2971-...)
 352a7f10... vendor/imgui (v1.92.6-docking-14-...)
 a15acd87... vendor/imguizmo (1.83-142-...)
 6fa36017... vendor/spdlog (v1.2.1-2510-...)
 f1c79c02... vendor/stb_image (heads/master)
 97d150e9... vendor/yaml-cpp (yaml-cpp-0.9.0-9-...)
```

> **原理**：`insteadOf` 把原本指向 github 的 URL 改写成指向本地 `.git/modules/vendor/<s>`，
> 于是 `submodule update` 变成纯本地文件操作。
> `protocol.file.allow=always` 是必需的 —— 新版 git 默认禁止 file:// 协议用于子模块克隆。
>
> ⚠️ 这会在 `.git/config` 里留下 `url.*.insteadOf` 条目。想清理掉（比如以后网络恢复了
> 想改回从 github 拉），执行：

```bash
ROOT="$(git rev-parse --show-toplevel)"

for s in $(git config -f .gitmodules --get-regexp '^submodule\..*\.path$' | awk '{print $2}' | sed 's|^vendor/||'); do
    if git config --remove-section "url.$ROOT/.git/modules/vendor/$s" 2>/dev/null; then
        echo "已清理 $s"
    else
        echo "跳过 $s（本来就没有该条目）"
    fi
done
```

> 也可直接手工删掉 `.git/config` 里对应的 `[url "..."]` 段。
> 清理后子模块**已拉下来的代码不受影响**（都在工作区里），只是后续 update 会重新走网络。
